# Klinik Amanah PostgreSQL Database Design

This document explains the database foundation in `schema.sql`. It is intentionally database-first and does not implement endpoints, ORM models, Docker, or backend modules.

## Design Summary

The schema is designed for one clinic: Klinik Amanah. It does not use a tenant model or repeat `clinic_id` across operational tables. The database still keeps clean boundaries between authentication, authorization, patients, staff, clinic units, services, schedules, appointments, queues, attendance, support, chat, notifications, exports, and audit records.

Patients are first-class authenticated users, but a patient profile may exist before the patient has a login. This supports both admin-created records and self-registration. Staff/admin users use the same `users` authentication foundation and receive access through RBAC.

The mobile review added a staff/doctor mobile operations layer. The Flutter app currently includes staff login, Google OAuth placeholder, forgot-password OTP, doctor dashboard, QR/manual/upload presensi, attendance history/export, doctor schedule management, leave/permission requests, doctor identity settings, biometric preference, IT FAQ, IT chat, and support tickets. Those requirements are now reflected in the schema without implementing mobile endpoints yet.

The clinical scope is deliberately lean. It supports medical intake forms and encounter records without prematurely modeling full EMR domains such as prescriptions, lab orders, billing, pharmacy stock, or insurance claims.

## Naming and PostgreSQL Conventions

- Table and column names use English `snake_case`.
- Primary keys are UUIDs generated by PostgreSQL with `gen_random_uuid()`.
- Timestamps use `timestamptz`; local clinical dates use `date`; clock slots use `time`.
- Stable lifecycle states use PostgreSQL enums, such as `appointment_status`, `queue_status`, and `staff_type`.
- Growing business data uses lookup tables, such as `clinic_services`, `medical_specialties`, `roles`, and `permissions`.
- Mobile/device state is modeled explicitly through `user_devices`; biometric secrets remain on-device and only a server-side preference/trust record is stored.
- Most mutable tables have `created_at` and `updated_at`, maintained by the `set_updated_at` trigger.
- Append-only join or log tables, such as `role_permissions`, `appointment_status_events`, `message_attachments`, and `audit_logs`, only store creation time.

## Table Responsibilities

### Authentication

`users` stores first-party authenticated identities. It intentionally keeps only auth-facing profile data: name, email, phone, image, status, locale, email/phone verification, and 2FA flag. Phone exists here because the mobile login form accepts either email or phone.

`user_devices` stores mobile and web device registrations. It supports device-scoped sessions, push tokens, app/platform metadata, last-seen tracking, revocation, and the server-side biometric-login preference. Biometric material itself must stay in the Android/iOS secure enclave or platform keystore, not in PostgreSQL.

`auth_sessions` stores server-side sessions. `token_hash` is named for secure digest storage instead of raw token storage. `device_id` links a session to a known device when the request comes from the mobile app.

`auth_accounts` stores credential and OAuth account bindings. Password hashes and encrypted OAuth tokens live here, keeping authentication methods separate from the user identity.

`auth_verifications` stores email verification, password reset, magic link, OTP, and two-factor verification records. Identifiers and values are hash-oriented to avoid storing reset tokens in clear text.

`auth_two_factors` stores TOTP/backup-code state for users who enable second-factor authentication.

### RBAC

`roles`, `permissions`, `role_permissions`, and `user_roles` implement RBAC. This supports the required role model:

- `admin`
- `staff_doctor`
- `staff_midwife`
- `staff_worker`
- `patient`

Roles are assigned to users, not directly to staff or patient profiles. This keeps login access independent from clinical identity.

### Clinic Catalog

`clinic_profiles` stores the single clinic's public and operational contact profile.

`clinic_units` stores operational units such as poliklinik, IGD, wards, departments, and IT support. This avoids forcing attendance filters and staff assignments into either `clinic_rooms` or `clinic_services`.

`service_categories`, `medical_specialties`, `clinic_services`, and `clinic_service_complaints` model services, poliklinik groupings, service-to-specialty mapping, queue prefixes, and quick complaint hints.

`clinic_rooms` models rooms used by schedules, appointments, queues, and attendance QR locations. A room can optionally belong to a clinic unit.

### People

`patient_profiles` stores medical-demographic identity. It links optionally to `users` because some patient records are created by admins before the patient has an account.

Sensitive identifiers are split into `national_id_hash` for exact lookup and `national_id_encrypted` for authorized display. The schema should not store raw NIK in plain text.

`patient_addresses`, `patient_emergency_contacts`, and `patient_allergies` normalize repeated patient details instead of flattening everything into `patient_profiles`.

`staff_profiles` stores clinic personnel and the required staff category: `doctor`, `midwife`, or `worker`. It also stores the staff member's primary unit, position title, and department label for mobile identity/settings screens.

`practitioners` stores appointment-capable clinical staff. It references `staff_profiles`, allowing a worker/admin staff record to exist without becoming bookable.

`staff_credentials` stores professional and legal identifiers such as SIP, STR, KKI number, NPWP, NIB, or NIK. Credential numbers are modeled as encrypted display values plus hash values for exact lookup/uniqueness. This is safer than storing legal identifiers as plain text on `staff_profiles`.

### Scheduling, Appointments, Queue, and Clinical Backbone

`practitioner_availability` stores recurring availability rules.

`practitioner_schedule_day_settings` stores doctor-level daily schedule controls such as target quota and day-level leave state. This matches the mobile calendar logic where a date has a target quota and can be marked as `cuti` independently from individual sessions.

`staff_leave_requests` stores the mobile leave/permission workflow: request type, date range, duration, reason, optional substitute doctor, status, reviewer, reviewer notes, and cancellation timestamp.

`practitioner_leave_periods` stores approved date ranges that affect actual practitioner availability. It can link back to `staff_leave_requests` when the leave originated from the mobile permission workflow.

`practitioner_schedule_sessions` stores concrete daily sessions with capacity, available slots, shift/session label, and status. This matches the web's doctor schedule view and the mobile doctor's schedule form, including Pagi, Siang, Malam, and Dini Hari sessions.

`appointments` is the central booking table. It links patients, practitioners, optional schedule session, services, rooms, status, visit type, scheduled date/time, complaint, optional guardian snapshot, and optional medical flow.

`appointment_status_events` keeps immutable status history, which is important for operational audit and queue progress.

`queue_tickets` stores live queue numbers issued from appointments. Queue numbers are unique per service and queue date. Mobile queue cards also require a queue priority such as regular, priority, BPJS, or VIP.

`medical_intake_submissions` stores structured intake answers as `jsonb`. The current pregnancy and immunization flows have many dynamic fields, so JSONB is the right boundary for the intake payload while the appointment and patient relationships remain relational.

`clinical_encounters` is the lean EMR backbone. It gives the backend a place to attach clinical notes and mark a visit as planned, in progress, completed, or cancelled.

### Attendance

`attendance_qr_sessions` stores QR presence windows using a hashed QR code identifier and rotation settings. It supports both location check-in QR codes and staff identity QR codes, plus optional manual PIN hash for the mobile "Presensi Manual" flow.

`staff_attendance_records` stores one attendance record per staff member, date, and shift. It supports present, late, missed, leave, and absent states; QR scan, manual PIN, upload QR, and system methods; expected/check-in/check-out times; late minutes; unit/room; source-code hash; and the device used for mobile submissions.

`user_data_export_jobs` stores asynchronous exports such as the mobile "Ekspor rekap presensi" PDF. The generated file links through the shared `files` table.

### Notifications

`notifications` stores message content, urgency, visual key, and source metadata. It covers web and mobile categories including queue, clinical/lab, shift, support, appointment, and system notifications.

`notification_actions` stores per-notification CTA buttons.

`notification_recipients` stores delivery, read, and dismissal state per user.

### Chat and Patient CRM

`conversations` groups patient chat activity and can reference assigned staff/practitioners.

`conversation_participants` tracks user participation, role, mute state, and read position.

`messages` stores text, audio, status updates, images, and file messages.

`files` centralizes uploaded file metadata. `message_attachments` links files to messages.

`patient_timeline_events` models the CRM sidebar timeline and links events to patients, conversations, and appointments.

### Mobile Staff Support

`support_faqs` stores published helpdesk FAQ entries and ordered solution steps for the mobile IT support settings screen.

`support_tickets` stores reported technical issues from staff or doctors, including ticket number, reporter, optional assigned support staff, title, status, priority, source channel, technician note, and resolution timestamps.

`support_ticket_messages` stores the IT chat thread around a support ticket. `support_ticket_attachments` links optional uploaded files to those support messages through the shared `files` table.

### Public Web Content

`clinic_facilities`, `public_testimonials`, and `public_reviews` provide optional backend-managed content for the public website without coupling public content to clinical records.

### Audit

`audit_logs` is append-only and records actor, action, affected entity, old/new JSON values, IP address, user agent, and timestamp. It is deliberately generic so all backend modules can write audit events.

## Relationship Design and Cardinality

- One `users` row can have many `auth_sessions`, many `auth_accounts`, many `user_devices`, many export jobs, and many active or historical `user_roles`.
- One `users` row can link to at most one `patient_profiles` row and at most one `staff_profiles` row.
- One `patient_profiles` row can have many addresses, emergency contacts, allergies, appointments, intake submissions, encounters, notifications through user, conversations, and timeline events.
- One `clinic_units` row can own many rooms, staff primary assignments, QR attendance locations, and attendance records.
- One `staff_profiles` row may become one `practitioners` row. Only practitioners are bookable for appointments. A staff profile can also have many credentials, leave requests, attendance records, and assigned support tickets.
- One `medical_specialties` row can classify many practitioners and services.
- One `clinic_services` row can have many appointments, queue tickets, and complaint suggestions.
- One `practitioner_schedule_day_settings` row belongs to one practitioner/date and can be referenced by many schedule sessions for that day.
- One `staff_leave_requests` row belongs to one staff profile and may reference a practitioner, substitute practitioner, reviewer, and approved practitioner leave period.
- One `appointments` row belongs to one patient, one service, and optionally one practitioner, schedule session, and room.
- One `appointments` row can have many `appointment_status_events`, one active `queue_tickets` row, zero or more intake submissions, and at most one `clinical_encounters` row.
- One `attendance_qr_sessions` row can be referenced by many attendance records.
- One `conversations` row belongs to one patient and contains many participants and messages.
- One `messages` row can have many files through `message_attachments`.
- One `support_tickets` row belongs to one reporting user, can be assigned to one staff member, and contains many support messages and optional attachments.
- Public testimonials can optionally link to a patient, but public reviews are independent because Google/manual reviews may not match a patient record.

## Indexing Strategy

The schema indexes the access patterns visible in the web app:

- Auth lookup: session token, active sessions by expiry, account provider identity, verification identifier/purpose/expiry.
- Mobile auth/device lookup: active devices by user/platform, unique push token hash, and session-to-device joins.
- RBAC lookup: active roles per user and permission joins.
- Clinic operations: unit type/activity and room-to-unit lookup.
- Patient admin table: patient name and medical record number trigram search, patient status, patient relations.
- Staff and doctor schedule: staff name search, staff type/status, primary unit, staff credential lookup, practitioner specialty, day settings, leave requests, and daily schedule sessions.
- Appointments: patient/date, practitioner/date/status, schedule session, service/date/status, appointment status, complaint search, status event history.
- Queue live view: queue date, service, status, and priority.
- Medical intake: patient/submitted date and JSONB GIN index on answers.
- Attendance dashboard and mobile history: attendance date, shift, status, staff/date history, unit/date filtering, and active QR session lookup by type.
- Notifications: unread recipient rows by user.
- Chat: conversation last activity, message ordering, and message body search.
- Support: published FAQ ordering, ticket lookup by reporter/status and assignee/status, and ticket messages by ticket/time.
- Exports: user/status/requested time for attendance PDF and profile export jobs.
- Audit: actor/time, entity/time, and action/time.

Partial unique indexes enforce important business rules:

- One active assignment for the same user and role.
- One credential account per user.
- One active appointment for a practitioner/date/start time.
- One conversation participant row per user per conversation.
- Unique national ID hash when present.

## Security Considerations

- Raw session tokens, verification tokens, and NIK values should not be stored in plain text.
- OAuth access, refresh, and ID tokens are modeled as encrypted values.
- Device identifiers, push tokens, attendance QR values, manual PIN values, and staff credential numbers are stored as hashes and/or encrypted values rather than raw secrets.
- Biometric login must be enforced by platform secure storage and the mobile client; the database only records whether a trusted device has biometric login enabled.
- Audit records include actor, IP address, and user agent for security review.
- RBAC is database-backed so API authorization can be enforced server-side, not only through navigation visibility.
- Password reset and email verification records have expiry and consumed state.
- 2FA records include failed-verification count and lockout timestamp.
- Medical intake answers use JSONB because the form schema is dynamic, but access must be controlled at the API/service layer.
- Support ticket attachments reuse the same `files` table so access scope, uploader, checksum, and file metadata remain centralized.
- Deleting core clinical records is restricted or cascaded deliberately: patients are protected from accidental hard deletion when appointments exist, while dependent addresses and allergies cascade.

## Backend Notes

- Better Auth can be configured with custom table and field names for the core user, session, account, and verification models.
- The backend should map Indonesian UI labels to English enum values at the API boundary. For example, `SUDAH DATANG` maps to `checked_in`.
- Mobile attendance labels should map to English enums: `hadir` → `present`, `telat` → `late`, `missed` → `missed`, and `cuti` → `leave`.
- Mobile permission labels should map to English enums: `Cuti Tahunan` → `annual_leave`, `Izin Sakit` → `sick_leave`, `Seminar / Simposium` → `seminar_symposium`, `Urusan Keluarga` → `family_matter`, and `Tugas Luar RS` → `external_assignment`.
- The backend should derive age from `patient_profiles.birth_date`.
- The backend should update appointment status through `appointment_status_events`, not by silently overwriting status.
- Reports should be derived from appointments, encounters, queues, attendance, and patients unless a materialized reporting layer is later required.
