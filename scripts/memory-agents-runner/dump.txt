  ### Implementation Summary: Notification Real-Time
  Infrastructure & Patient Appointment Lifecycle
  All planned milestones across the real-time notification
  infrastructure, patient call attempt & requeue lifecycle,
  patient appointment history API, validation seeder, and API
  contracts are 100% completed and verified.
  ──────
  ### Architectural Highlights
  1. Hexagonal Architecture (Ports & Adapters):
      • Built a transport-agnostic notification engine where
      business modules publish domain events (DomainEvent)
      through an abstract port (NotificationPublisher).
      • Event formatting and delivery rules are registered
      dynamically at bootstrap via NotificationRulesRegistry,
      ensuring zero tight coupling between domain modules and
      notification channels.
  2. Enterprise Reliability & Deduplication (SSOT &
  Idempotency):
      • Persistence First: In-app notifications are persisted
      to PostgreSQL before real-time socket delivery is
      attempted.
      • Deterministic Idempotency Key: Uniqueness is enforced
      at the database level (idempotency_key unique index on
      notifications table) with the formula
      eventId:recipientId:eventType. Replays or duplicate
      stream deliveries safely return null and skip channel
      emission.
      • Offline Resilience: Offline clients retrieve unread
      and historical notifications upon reconnecting through
      REST history reconciliation.
  3. Three-Layer Real-Time Transport:
      • Durable handoff to Redis Streams via stream
      notifications:events and consumer group notification-
      service.
      • Dedicated background stream worker
      (NotificationStreamWorker) processing messages with
      XREADGROUP and XACK.
      • Socket.IO Gateway (SocketIoRealtimeGateway) mounted
      at /socket.io with Bearer JWT handshake verification,
      joining private client rooms user:<userId>.
  4. Patient Call Attempt & Requeue Lifecycle Policy:
      • Implemented in AppointmentCallLifecycleService (< 300
      LOC) and backed by appointmentCallAttempts table.
      • Enforces a maximum of 3 call attempts
      (MAX_PATIENT_CALL_ATTEMPTS = 3).
      • Attempts 1 & 2: If missed, attempt status is marked
      no_response, queue ticket is requeued with status:
      'waiting' bumped behind 3 positions, and event
      appointment.patient_requeued.v1 is emitted.
      • Attempt 3: If missed, appointment transitions to
      terminal no_show, queue ticket transitions to skipped,
      and urgent event appointment.no_show.v1 is emitted.
  5. Unified Patient Appointment History Query API:
      • Created PatientAppointmentHistoryService and
      PatientAppointmentHistoryController (< 100 LOC).
      • Scoped strictly to patient appointments and terminal
      states (completed, cancelled, no_show).
      • Supports endpoints: GET
      /api/v1/appointments/history/me (mobile patient) and
      GET /api/v1/appointments/history/patient/:patientId
      (staff / web portal).
  6. File Size Discipline:
      • Every file created or updated strictly adheres to the
      rule: No single source file may exceed 500 lines of
      code (highest is 432 lines).
